01 / Executive readout

Good foundations, buried proof

The portfolio has personality, real interaction work, and stronger-than-average admin authentication. The product story and assurance story are both less mature than the underlying effort.

The current site feels like a collection of polished experiments inside a narrow bento column. It does not yet answer the hiring-manager question quickly enough: what does Sarang build, how well does he build it, and what changed because of his work? The redesign should make evidence the main event and let playfulness support it.

Visual clarity 5.5/10 Subjective heuristic score
Accessibility 5/10 Manual code and tree review
Performance 6/10 Build and sampled responses
Maintainability 7/10 Typed, tested, some dead paths
Security gate See checklist Scoped fixes verified
A literal promise of zero vulnerabilities would still be false.

The scoped blockers from this review have been remediated and are recorded in the completed checklist. Independent static analysis and penetration testing remain necessary before making a broader assurance statement.

What is working

  • The map, typing simulator, doodle board, and subtle motion create a recognizable personality.
  • Cloudflare Access, passkeys, strict origin checks, short sessions, D1 prepared statements, and Turnstile form a serious admin foundation.
  • Lint, TypeScript, 70 tests, and the production build pass.
  • The generic entity plugin/repository pattern is proportionate and keeps admin CRUD consistent.
  • The mobile layout remains usable and avoids catastrophic overflow in the inspected routes.

What is holding it back

  • A roughly 550px desktop column leaves most of the viewport unused and compresses the visual story.
  • Nested pale cards, low contrast, and similar section treatments flatten hierarchy.

03 / Visual direction

Precision workshop

Keep the site's wit, but make the dominant impression: an engineer who ships thoughtful systems. The map becomes the signature surface; proof, not cards, creates hierarchy.

Audience and job

Primary audience: hiring managers, engineering leaders, and peers scanning in under two minutes.

Primary job: establish role, technical range, judgment, and measurable evidence before asking for deeper exploration.

Secondary job: reward curiosity through the map, playground, writing, and visitor board.

Design rules

  • Use a 1040-1120px content field on desktop and one column on mobile.
  • Reserve cards for repeated project items or true tools; use full-width bands elsewhere.
  • One strong visual move per viewport, supported by quiet typography and rules.
  • Use motion to explain state, never to delay access to content.
  • Put screenshots, outcomes, and real artifacts before logo grids or contribution counts.

04 / Page findings

Page-by-page plan

These observations came from the production site, with source review used to explain behavior and define acceptance criteria.

Home

Strong ingredients, weak hierarchy

The desktop page is constrained to roughly 550-576px, leaving large unused margins. Map, profile, experience, projects, playground, stack, and contributions receive nearly equal visual weight through repeated pale containers. Full-screen particles cross text and controls, while the most credible proof - project media and outcomes - is absent.

Plan: widen the field; make the map the hero background; add a concise role/value statement; place a three-item proof rail beneath it; lead with two or three case studies; convert experience to rows; consolidate playground experiments behind tabs; demote stack and contribution volume.

Observed at sarang.dev; layout source: src/app/(public)/page.tsx and src/app/(public)/layout.tsx:18-21
Projects

Too little evidence for a primary destination

The live page presents one compact project row and then a large empty field. There is no screenshot, role, challenge, architecture, tradeoff, result, or link context. An accepted project URL may also be #, which produces a visually valid but functionally dead action.

Plan: ship three case studies with a consistent evidence schema: context, role, constraint, technical choice, measurable/observable outcome, stack, and actual media. Keep smaller experiments in a separate lab index. Reject placeholder links from published content.

src/lib/admin/schema/url.ts:3-33; src/components/home/project-item.tsx:43-54
Header

Mobile density needs a deliberate mode

At 390px, Sarang and the primary routes still compete for space in one row. This is a visual-information-architecture decision and remains outside the current fix scope.

Remaining plan: keep the name and two primary routes visible and move secondary routes into a compact menu without changing the wider desktop navigation.

src/components/ui/header.tsx:36-43
Admin

Keep it utilitarian; improve form semantics

The generic entity form is a reasonable internal abstraction, but visual labels are not consistently associated with fields. Security-sensitive operations should visually distinguish routine edits from credential and destructive actions.

Plan: preserve the dense sidebar/table workflow, associate every label and error with its control, add clear destructive confirmation, show session freshness for credential operations, and add operational status for backups/retention.

src/components/admin/EntityForm.tsx:301-305; src/lib/admin/actions/auth.ts:62-95

08 / Security strengths

Controls worth preserving

The audit is not a teardown. Several implementation choices are thoughtful and should remain intact while the gaps above are fixed.

Identity and session

  • Cloudflare Access JWT verification binds expected issuer and audience against remote JWKS.
  • Passkey verification requires user verification and checks expected RP ID and origin.
  • Admin cookie uses the __Host- pattern, Secure, HttpOnly, SameSite, a short lifetime, and stored-session validation.
  • Session MAC comparison is constant-time and uses HMAC-SHA-256.
  • Write actions enforce same-origin checks and sensitive deletion already uses fresh authentication.

Input and platform

  • D1 values use prepared statements; dynamic table/column identifiers come from an internal registry.
  • Turnstile validates expected action and hostname and fails closed when its secret is missing.
  • Visitor uploads are streamed with an 850KB cap, PNG signature/dimension checks, normalized text, and UUID identifiers.
  • Artwork URLs are HTTPS-only and hostname-allowlisted; Cloudflare public-fetch enforcement reduces private-network SSRF risk.
  • Admin CSP uses nonces; HSTS, nosniff, frame denial, and restrictive form/base directives are present.
  • Dependabot/OSV workflow and npm audit currently report no known dependency advisories.
09 / Delivery plan

Five phases, security first

The sequence avoids polishing broken content or building a design system on top of known security debt. Time ranges are planning estimates for one experienced engineer, not commitments.

Phase 1
1-2 days

Repair content and information architecture

  • Publish at least three substantive projects and two real articles before visual expansion.
  • Write one-line positioning, proof-rail facts, case-study outcomes, and clear action labels.
Exit: every listed post/project opens successfully in a production-like build; content smoke tests pass; no placeholder action is published.
Phase 2
2-4 days

Build the visual system and home narrative

  • Introduce the neutral/cobalt/green/coral token set and new typography roles.
  • Implement the 12-column desktop field and one-column mobile layout.
  • Turn the Bangalore map into an unframed hero with static-first rendering.
  • Build screenshot-led case studies, proof rail, experience rows, and a single lab band.
  • Remove nested cards, global particles, hue cycling, and fake loading.
Exit: name, role, proof, and one project are understandable in the first viewport; a hint of next content is visible at 390, 768, 1280, and 1440px.
Phase 3
2-3 days

Accessibility and performance hardening

  • Capture production-like performance traces before and after.
Exit: keyboard and screen-reader journeys pass; no serious/critical automated accessibility findings; performance budgets below are met or deviations are documented.
Phase 4
1-2 days + ongoing

Independent assurance and operations

  • Run Semgrep/CodeQL, secret scanning, dependency review, and authenticated DAST in staging.
  • Exercise backup restore, alerting, key rotation, and retention jobs.
  • Commission an independent penetration test for admin and public upload/proxy surfaces.
  • Document residual risks and an owner/target date for every accepted item.
Exit: no known critical/high finding, all medium items fixed or explicitly accepted, restore drill succeeds, and evidence is retained with the release.

11 / Limits and residual risk

What this report cannot prove

Security confidence comes from multiple independent methods over time. This is a strong manual review and planning artifact, not a certification or warranty.

  • No production admin account, Cloudflare dashboard, D1 data, R2 policy, secret store, or Access policy was inspected.
  • No destructive penetration test, fuzzing campaign, race harness, authenticated DAST, or exploit demonstration was run.
  • No complete Semgrep or CodeQL taint scan was executed; their future findings may add or reprioritize issues.
  • No dependency-maintainer provenance or takeover-risk investigation was performed beyond lockfile advisory checks and workflow review.
  • No field Core Web Vitals or controlled lab trace was captured; performance estimates are directional.
  • Production content and infrastructure can change after July 12, 2026; findings should be revalidated against the release candidate.
  • Even after every listed item is fixed, zero vulnerabilities cannot be guaranteed. The defensible statement is “no known critical/high issues under the tested scope as of a specific date.”
Recommended final security statement

“The release passed automated quality, dependency, static-analysis, accessibility, and targeted penetration checks; no known critical/high findings remain within the documented scope. Residual risks and test limitations are recorded.”
